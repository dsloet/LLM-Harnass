1

Summary

A language model produces text. Risk appears the moment that text is connected to something that acts: a shell, a file system, a database, a mailbox or the internet. The software that sits between the model and those systems is called a harness. It decides what the model may do, records what it did, and limits the damage when the model is wrong or has been manipulated. A model downloaded from the internet comes without that layer.

The model proposes, the harness decides

Every action passes a policy check that runs in code the organisation controls. Unknown actions are refused or sent to a person, never allowed by default.

Prompt injection is not solved

No current model reliably ignores instructions hidden in emails, web pages or documents. Limiting what the model can reach is the main defence.

Audit what the model saw

Every model call should leave a record of the exact context, where each piece came from and how far it can be trusted. Without it, a decision cannot be explained or defended.

Treat downloaded weights as untrusted code

Model files can execute code when loaded, and model behaviour can contain hidden triggers. Origin and integrity must be checked before use.

Origin matters, controls matter more

Published tests show some Chinese open-weight models are easier to hijack. The same harness applies to every model; a weaker model needs stricter settings.

2

What a harness is

Harness engineering is the practice of building the environment around a model rather than the model itself. A public tutorial that rebuilds a commercial coding agent from scratch (Khan, 2026) describes four principles: the model makes decisions, tools are the only way it touches the world, context is a managed resource, and permissions are set in configuration rather than scattered through code.

For risk management the important consequence is a separation of duties. The model can only ask for an action. Whether that action runs, in what environment, with which rights, and how it is recorded, is decided by code that the organisation owns and can audit.

Weak defaults to avoid

Having a harness is not enough. The tutorial's own implementation, which is written for teaching, shows how small design choices undo the protection. These are common patterns and useful test cases for any harness an organisation builds or buys.

PatternWhat goes wrongBetter default
Allow when no rule matchesAny command nobody thought of runs without a check. In the tutorial, the code allows unmatched commands while its own diagram says they go to a person.Deny or ask when no rule matches.
Text patterns as security rulesls && rm -rf data/ matches the "always allow" rule for ls and runs silently. A deny rule for rm -rf / misses rm -rf ~, find / -delete and deletes through a scripting language.Allow lists of exact tools and arguments, a parsed command, and a sandbox that limits damage regardless of the command.
Hooks that fail openA security hook that crashes is logged and skipped, so the action it should have blocked goes ahead.A failing security hook blocks the action.
Undo that only covers some actionsSnapshots cover the file-write tool and live in memory. Deletes through the shell are not covered, and all snapshots disappear when the process stops.Work on copies or in version control; backups outside the agent's reach.
Logs the agent can editThe log is a local file in the agent's working folder, and inputs are cut to 60 characters.Full inputs, written to append-only storage the agent cannot reach.
External tools trusted on sightExternal tool servers are registered automatically. Their tool descriptions go straight into the model's context and can carry instructions.An approved list of servers, with descriptions reviewed and pinned.
Self-written instructionsThe agent can write a new instruction file and load it, and its memory file is reloaded every session. Injected text can persist this way.Instruction and memory changes go through review before they take effect.
Shell commands built from model textCommands run through a shell with the model's text as input, which the agent's own code review flags as an injection path.Call programs with argument lists, inside a sandbox.

The tutorial also makes claims about the internals and revenue of the commercial product it imitates, based on what it calls reverse-engineered traces. These claims are not confirmed by the vendor. The tutorial is useful as an illustration of harness patterns, not as a description of any specific product.

Context provenance and decision audit

A model decides on the basis of its context: the rules, the request, the records and the documents placed in front of it for that call. For an audit, two questions matter. What did the model see? And what did it use? The first can be answered completely. The second can only be narrowed down.

Many harness features that save cost or context space also remove provenance. The tutorial shows several of them:

MechanismWhat happens to provenance
Context compressionOlder turns are replaced by a summary the model writes itself. Later decisions rest on that summary, with no link back to the original records. The summary can contain errors or injected text, and it is reloaded every session.
Sub-agentsThe main agent only receives the sub-agent's final text. The file reads and searches behind it are discarded, so the main decision has no evidence trail.
Background notificationsResults from background tasks are inserted into the conversation as if the user had written them. Tool output then carries the authority of a person, and the log cannot tell the two apart.
Instruction files loaded on demandInstructions arrive as tool results from files the agent can edit. A log line that says which file was loaded does not say which version.
Memory and task files on diskPersistent and writable by the agent, with no record of who wrote each line, when, or why.
External tool serversData from outside servers enters the context without a source label or trust level.
Fully solvable

Record what the model saw

  1. A context manifest for every model call: source ID, source system, version or hash, retrieval time, trust level and who could access it. Keep the full assembled prompt.
  2. Separate instructions from data: external and tool content goes into marked data blocks. Tool output is never inserted as a user message.
  3. Traceable compression: summaries keep links to their source records and are stored as versioned, derived items. Originals are archived, not deleted.
  4. Keep sub-agent evidence: log each sub-agent's tool calls and sources under the parent session ID.
  5. Access checks at retrieval time: filter records by the end user's rights before they enter the context.
  6. Tamper-evident storage: append-only, hash-chained entries, stored outside the agent's reach, with retention rules and access control.
  7. Pin everything needed for replay: model version, settings, prompt template version, tool versions and the manifest.
Partly solvable

Narrow down what the model used

  1. Require citations to source IDs for every factual claim or decision input.
  2. Verify citations in code: each cited ID must appear in the manifest, and quoted text must appear in that source. Flag or reject answers that fail.
  3. Leave-one-out tests for decisions that matter: re-run without a given source and check whether the outcome changes. This shows which data actually drove the decision.
  4. Do not treat stated reasoning as an audit trail. Research on reasoning models shows they do not always state the real basis for an answer. Use it as a hint, not as evidence.
  5. Human review for decisions about people, with the cited sources visible to the reviewer.
7

Model origin: Chinese open-weight models

Prompt injection affects every current language model, whatever its origin. The question is whether some models are measurably easier to manipulate, and whether origin changes the data-breach picture. Published tests point to an additional risk for at least one family of Chinese models.

StudyFindingHow to read it
NIST CAISI, September 2025Agents built on DeepSeek's most secure model tested (R1-0528) were on average 12 times more likely than the US frontier models tested to follow malicious instructions that hijacked them away from the user's task.Hijacking is the mechanism behind data exfiltration and unwanted actions. This is the most direct evidence of added agent risk.
Cisco and University of Pennsylvania, early 2025An automated jailbreak got harmful answers from DeepSeek R1 on all 50 sampled HarmBench prompts.The same test gave 96% for Llama 3.1-405B and 86% for GPT-4o. Weak resistance is common among models in general, and DeepSeek R1 scored worst.
CrowdStrike, 2025DeepSeek-R1 wrote less secure code when a prompt mentioned topics such as Tibet, Uyghurs or Falun Gong. Coverage reports up to 50% more severe vulnerabilities.Content rules applied in training can change technical output in ways a user would not expect. Figures come from press coverage of the study.
Anthropic and others, "Sleeper Agents", 2024Deliberately planted trigger behaviour survived standard safety training, and adversarial training sometimes hid it better.Applies to any unverified weights. It shows that testing alone may not reveal a backdoor.

These findings concern DeepSeek models. Other Chinese model families were not covered by the studies listed here and should not be judged on these results.

Data breach

Hosted service: prompts and data are sent to the provider and fall under the provider's jurisdiction. For a Chinese provider that is Chinese law. Check the provider's current privacy policy before any use with personal or confidential data.

Local weights: the extra risk is behavioural. A model that is easier to hijack will more readily use whatever tools and network access it has been given to move data out.

Misalignment and hidden behaviour

Planted trigger behaviour can survive safety training, and this applies to any unverified weights. For models from a jurisdiction where the state can direct companies, the question of who might plant such behaviour is more serious.

This review found no public proof of a deliberate backdoor in a Chinese model. What is documented is weaker resistance to hijacking and content rules that affect technical output.

Recommendation. A Chinese open-weight model can be acceptable for some uses, but treat it as an untrusted component with stricter harness settings: no network egress, a sandbox without secrets, human approval for every action that leaves the system, and a red-team test on the organisation's own tasks before production. Do not use the hosted service for personal or confidential data.

Regulatory notes

  • GDPR, Article 22. Limits decisions based solely on automated processing that have legal or similarly significant effects on a person, and gives the person a right to human intervention and to contest the decision. That right cannot be met without knowing which data a decision used.
  • EU AI Act. For high-risk systems, Article 10 sets requirements for data and data governance, and Article 12 requires automatic logging of events. AI used in employment and worker management is among the listed high-risk areas. Whether a given use case is high-risk depends on its purpose.
  • Model licences. Open-weight models come with their own licence terms, which can restrict commercial use or require attribution. Record the licence with the model version.

These notes are a starting point, not legal advice. Confirm the applicable articles and their scope with legal counsel.

9

Minimum control baseline

A practical order of work. Each phase should be complete before the next starts.

Phase 1

Before a pilot

  • Named owner and written policy for what the model may do
  • Model downloaded from the original publisher, hash verified, safetensors format
  • No remote code execution when loading the model
  • Sandbox or container with a separate service identity
  • Network egress blocked by default
  • No secrets or production credentials in reach
Phase 2

Before connecting company data

  • Policy gate that denies or asks when no rule matches
  • Human approval for every irreversible or outbound action
  • Access filtering at retrieval time
  • Context manifest and full prompt stored per model call
  • Append-only audit log outside the agent's reach
  • Data protection impact assessment completed
Phase 3

Before production

  • Prompt injection and hijacking tests on the organisation's own tasks
  • Citation checks for answers that feed decisions
  • Human review for decisions about people
  • Step, time and budget limits with a kill switch
  • Pinned versions of model, harness, prompts and tools
  • Scheduled re-evaluation and log review
